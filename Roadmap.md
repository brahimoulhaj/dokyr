# Dokyr — Roadmap

Implementation tracker for the single-node PaaS panel. Source of truth for the design is the
architecture doc ("Single-node PaaS panel: architecture and data model"). The product is named
Dokyr (dokyr.com, earlier working name Berth); the name lives only in `internal/brand/brand.go`.

**How to use:** tick a box only when the item is built *and* verified (test or manual run).
`[ ]` not started · `[~]` in progress · `[x]` done.

**Progress:** M0 ◐ (sqlc started: two stores of about thirty) · M1 ◐ (users and roles, host terminal and cron jobs in; email invites, more owners, per-project access, VPS checks left) · M2 ◐ (nearly done: Gitea token left; Nixpacks not yet deployed through the panel) · M3 ◐ (TLS modes, redirects, Certificates page left) · M4 ◐ (instances, users/grants with drop and password rotation, Adminer, S3 backups/restore/deletion, daily/weekly/cron retention policies, whole-instance backups, backups of deleted instances, public ports; checked on the VPS) · M5 ◐ (registry done and checked on the VPS; built-in S3 per-bucket keys in; a real domain and VPS checks left) · M6 ◐ (container metrics with history and charts; notifications and alert rules; continuous health monitoring; usage threshold alerts; MongoDB and ClickHouse remain) · M7 ◐ (remote CLI started: `cmd/dokyr` with browser sign-in, `status`, `logout`, `projects list` and `projects create`, sign-in and list checked on the VPS; device flow, contexts, the other commands and releases left) · Cross-cutting ◐ (docs and security review done, with open security findings in `docs/security.md`; install e2e written, not yet run)

**Where we are (2026-11-19, v0.30.0):** A security release that closes the maintainer role's way to the host. Until now a maintainer could mount any host path into an app (the Docker socket included), choose a Buildpacks builder image (it runs as root with the socket), move the panel's own domain and then claim the old hostname for an app (browsers still send the session cookie there), and change the settings an admin owns. Now bind mounts and the Buildpacks builder image are for owners and admins to add or change (a maintainer keeps editing around ones an admin set), the panel domain, updates, panel backups, object-store and registry settings and notification channels are `adminOnly`, hostnames the panel used to answer on are remembered (`panel_domains_retired`) and only an admin may route one, no access key is made for a bucket that holds the panel's backups, and Git, GitLab and S3 addresses on the server's own networks need an admin (`internal/api/privileged.go`). The proxy adds a per-start secret header, so `X-Forwarded-For` is believed only from it and an app container cannot pick its own address. Also: a saved SMTP password does not follow a channel to another host, the Nixpacks output folder may not hold a symbolic link, Git host and webhook clients do not follow redirects, deploy-hook tokens are hidden in the request log, the storage hostname is reserved, secret build variables cannot take names the build tools read, the public database gate caps connections in its handshake, and the pages carry a Content-Security-Policy and HSTS. The web UI hides what a maintainer can no longer do. `TestMaintainerCannotReachHost`, `TestPanelDomainIsAdminOnly`, `TestAdminOnlyOperations`, `TestMaintainerStorageKeys`, `TestMaintainerInternalAddresses` and `TestSecurityHeaders` pass with the rest of the Go tests and the web build; the hidden controls were checked in the browser as a maintainer and as an admin. Not yet checked: a real GitHub App manifest flow under the new CSP, the proxy token on a real Caddy after a panel restart, anything of this version on the VPS. ### Strategies
- [x] Rolling: start new → health check → patch Caddy upstream → drain (default 10 s) → remove old — after the switch the old container keeps running for the app's drain (Health check settings → Drain, 0–300 s, default 10; `0016_health_check_drain.sql`; an API call without `drain` gets the default), then gets SIGTERM and `StopGrace` (10 s) before it is killed and removed. - [x] Rolling failure path: remove new, leave route untouched, mark failed — what every failed deploy already does (`TestDeployFailureKeepsOldContainer`)
- [x] Recreate: stop old → start new → health check → roll back to previous image on failure — after the pull or build (and the mount check), phase `stopping` stops every running container of the app (kept, `StopGrace`), then start and health check as usual; no drain. ## M7 — Remote CLI

Goal: manage a panel from a personal machine, the way `doctl` or `gh` do: install one
binary on a laptop, sign in through the browser against your own panel, then deploy and
look at things from the terminal. The CLI on the server (`dokyr setup-token`, `owner`,
`update`, `restore`) stays what it is: it works on the data directory and needs root there.
This one only speaks the HTTP API, as a user, with that user's role.

### Client binary (`cmd/dokyr`)
- [~] A client of its own, apart from `cmd/panel`: no store, Docker or web app inside, only the API client; macOS, Linux and Windows, amd64 and arm64 — `cmd/dokyr` (`make cli` writes `bin/cli/dokyr`), on Cobra for the commands, Lip Gloss for the output and Huh for prompts and spinners (colours, frames and prompts in a terminal only; a pipe gets plain text); built and run on macOS arm64 only, no release builds yet
- [ ] Naming: the installer's host command on the server is also called `dokyr`; decide whether the client takes the name on the server too (it would wrap the container CLI for the local commands) or the two stay apart
- [~] Config in the user's config directory (`~/.config/dokyr/config.json`, mode 600): contexts, each a panel URL, a user and a token; the token in the OS keychain where there is one, in the file otherwise — the file with its contexts is in; the token is in the file everywhere, no keychain yet
- [ ] Contexts for more than one panel: `dokyr context list|use|remove`, `--context` and `DOKYR_CONTEXT` for one command
- [ ] `DOKYR_URL` and `DOKYR_TOKEN` for CI, where no browser sign-in happens: an API token from Settings works as it does today

### Sign-in through the browser
- [x] `dokyr login https://panel.example.com`: opens the browser on the panel, the user signs in there as usual (password, passkey, GitHub) and approves the device; the CLI never sees the password — a sign-in that passes through the sign-in page comes back to the approval (kept in the tab's session storage)
- [x] The flow: the CLI listens on a loopback port, opens `/cli/authorize` with a state and a PKCE challenge, the panel shows who asks (device name, a short code also printed in the terminal) and redirects back to `127.0.0.1` with a one-time code, which the CLI exchanges for a token
- [ ] Without a browser on the machine (SSH session): `dokyr login --no-browser` prints a URL and a code to type on another device, and polls until it is approved (device flow)
- [x] API: `POST /api/cli/authorize` (start), the approval page in the web app (session only, same-origin), `POST /api/cli/token` (exchange); one-time codes hashed, valid a few minutes, rate-limited like sign-in — `internal/api/cli_login.go`; pending codes are held in memory (5 minutes), not in the database
- [~] The token is an API token of that user, marked as a CLI sign-in with the device name: listed in Settings → API tokens and Settings → Security with last use, revocable there, ended with the user. A token still cannot create tokens — an API token named `CLI on <device>`, listed and revocable under API tokens; the mark is the name only (no column), and it is not shown under Security
- [x] `dokyr logout` revokes the token on the panel and forgets it; `dokyr whoami` shows the panel, the user and the role — `dokyr status` (alias `whoami`, `--json`) asks the panel and fails when not signed in; `logout` calls `POST /api/cli/logout`, where a token ends itself and no other, and forgets the token here even when the panel is unreachable or too old
- [x] Plain-HTTP panels (`http://<server-ip>`): refuse by default, `--insecure` to go on with a warning; the loopback redirect and PKCE keep the code from other local programs — a panel on a loopback address needs no flag

### Versions
- [ ] The CLI reads the panel's version at sign-in and on each command (`/api/meta`), and says so when the panel is older than a command needs or newer than the CLI knows: "this panel is v0.31.0; `dokyr logs --follow` needs v0.33.0", "update the CLI"
